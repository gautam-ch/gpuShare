Kinetic — Decentralized Peer-to-Peer GPU Slicing & Sharing Platform

Kinetic is an open-mesh computing marketplace enabling local machine learning acceleration by pooling consumer-grade GPU hardware through secure containers, Tailscale overlays, and user-space memory virtualization.

Application Name: Kinetic
Project Mentor: Dr. Bheemappa Halvar
Core Stack: FastAPI, Next.js, Electron, Docker, Tailscale, Cloudflare
Project Theme: Decentralized GPU Clouds
02 / The Challenge

Why Peer-to-Peer GPU Sharing?

01. Cloud Monopoly & Cost

Enterprise GPU cloud providers (AWS, GCP) maintain high pricing premiums, making multi-gigabyte VRAM allocations inaccessible for individual researchers, college students, and bootstrap startups.

02. Underutilized Hardware

Consumer PCs running high-tier RTX series GPUs remain idle up to 85% of the day. There is no off-the-shelf mechanism to monetize or share these isolated resources.

03. Slicing & Network Barriers

NVIDIA restricts hardware GPU Slicing (vGPU/MIG) to enterprise cards (A100/H100). Consumer cards lack hardware virtualization, and local hosts are trapped behind strict home routers/NATs.

04 / Core Innovation

Software-Defined GPU Slicing

  • →
    User-Space Interception
    Injects sitecustomize.py inside the container system path, intercepting model training packages (`torch`, `tensorflow`) instantly on import.
  • →
    Fractional VRAM Allocation
    Limits PyTorch allocations dynamically via `torch.cuda.set_per_process_memory_fraction()`, forcing memory caps on RTX cards without needing MIG hardware.
  • →
    Dual-path Telemetry Fallback
    Saves process usage inside the container to `/tmp/gpushare_usage_*.json` to bypass container boundaries, serving telemetry directly to the host watchdog daemon.
    • 05 / Control Plane

    FastAPI Hub & Matchmaker

  • ✓
    Capability Matchmaking
    Matches renter specifications (VRAM, CPU cores, RAM limits) against live providers, allowing a VRAM match threshold to account for host display overhead (~300MB).
  • ✓
    Dynamic Installer Scripts
    Generates customized scripts (`/install-script`, `/install-script-windows`) injecting a single-use Tailscale AuthKey. Automates setup via curl/PowerShell pipes.
  • ✓
    Dual Database Support
    Supports lightweight local SQLite migrations for developer environments and auto-detects Railway PostgreSQL connection strings for production.
    • Matchmaking Logic Snippet
    def rent_gpu(db, vram_required):
    vram_mb = vram_required * 1024
    # Match threshold: allow 15% tolerance
    vram_match_threshold = max(vram_mb - 512, vram_mb * 0.85)
    
    # Filter active, online machines
    machine = db.query(Machine).filter(
        Machine.status == "online",
        Machine.vram_free_mb >= vram_match_threshold
    ).first()
    return machine
    06 / Hardware Security

    Host Agent & Safeguards

  • ⚠
    Thermal Guard Safeguard
    Watchdog loop polls GPU metrics continuously. Automatically halts all containers and tunnels if GPU temperature triggers safety limits (≥ 88°C).
  • ⚠
    System Memory Recovery
    Halts renter pods and releases host memory reserves if host RAM utilization pins at 96% for 3 consecutive sweeps.
  • ⚠
    Cgroup CPU/RAM Enforcements
    Caps renter usage parameters inside Docker. Kills violating sub-processes utilizing standard host kernel `SIGKILL` commands.

    07 / Connectivity Mesh

    Zero-Config Networking Flow

    Control Plane (Hub ↔ Host)

    Secured via Tailscale VPN Overlay Mesh.

  • ▪ Host executes script, authenticates without browser, joins private Tailnet.
  • ▪ Hub queries health and dispatches workloads using private 100.x.x.x IP channels.
  • ▪ No open router ports, firewall edits, or static DNS configuration required.
    • Data Plane (Renter ↔ Container)

    Routed via Cloudflare Quick Tunnels.

  • ▪ Host starts Jupyter Notebook, then binds local proxy tunnel using `cloudflared`.
  • ▪ Cloudflare provides a public ephemeral URL (e.g. `*.trycloudflare.com`).
  • ▪ Renters access Jupyter Lab directly via HTTPS without installing Tailscale.

    09 / System Lifecycle

    Rental Spawner Workflow

    1
    Heartbeat & Match
    Host registers capabilities. Renter requests resources, Hub matches machine.
    2
    Container Start
    Host maps volume mounts and starts Jupyter container with hard CPU/RAM cgroup limits.
    3
    Limits Injected
    sitecustomize.py intercepts imports, setting limits dynamically.
    4
    Tunnel Active
    Host starts cloudflared, returns ephemeral public URL to Hub for Renter routing.
    5
    Watchdog & Exit
    Host guards limits. User ends rental, Host terminates container, freeing hardware.
